The AI Delegation Loop

Stop building a new AI agent for every job. Give one capable AI a clear playbook for each repeatable task, a toolbox it can reuse, and checks that prove the work is done.

This is the expanded companion to the AI Delegation Loop reel. It is designed so you can start from an empty folder and build a working first playbook.

Important distinction. “AI Delegation Loop” is the teaching framework used in this guide. Anthropic's published Agent Skills approach uses instruction folders and a SKILL.md file. Anthropic has not stopped building agents, and multiple-agent designs still have valid uses. This guide focuses on a simpler starting point for repeated work.

Why your agents keep breaking

You get excited about AI. You build an agent for email, another for content, one for research, and another for follow-ups. Before long, you have a collection of half-finished systems. Each has its own prompt, files and setup. Change one thing in your process and the same correction must be made in several places.

Often the missing ingredient is not a smarter model. It's your job knowledge: the decisions you make without thinking, the template you always reach for, and the checks you perform before sending anything out.

A more manageable starting point is one capable AI environment with reusable instructions for different jobs. Anthropic describes this kind of reusable packaging through Agent Skills, which combine instructions, scripts, and reference materials. It does not mean one agent is always better for every technical use case.

Before you begin: choose one job

Don't start with the most complicated task in your business. Choose one you repeat at least weekly, one where you recognise a bad result immediately, and one you can explain to a new teammate in about twenty minutes.

Examples include a weekly client report, turning a long video into short-form posts, sending invoice reminders, or reviewing applications against an agreed scorecard.

Where the playbook lives

With Claude Code or another tool that has file access: make a real folder on your computer or repository. The AI can create and update files when you give it the appropriate permissions.

With browser-based ChatGPT or Claude: keep a master folder locally or in your Drive, then upload the current playbook files into the tool you're using. Unless your chosen tool explicitly supports writing back to that connected location, an AI-generated change in chat does not automatically replace the master file. Save the new version, then update the uploaded copy.

One master copy. Avoid multiple competing versions of the same playbook. Never put passwords, API keys, or sensitive personal data into a shareable folder or public GitHub repository.

Layer 1

The process: get your decisions out of your head

Your playbook begins with an interview. Ask Claude or ChatGPT to question you about what triggers the job, which files you use, the order of your steps, where you make judgement calls, and the mistakes that have happened before.

Why an interview? Because you may forget to document things you do automatically. Maybe you always begin a client update with the biggest change in the numbers. Or you never publish a reel without reading the hook aloud. Those details are what help the output match your actual work.

For a Claude-compatible Skill, use a SKILL.md containing a short description plus the instructions. If you are using a chat-only setup, a normal Markdown playbook with the same content is useful too, even if it is not installed as a native Skill.

Prompt 1: turn your job into a playbook

Copy-paste prompt · 01 / Interview + process
Help me turn a task I do repeatedly into a documented AI playbook.

The task is: [DESCRIBE ONE REPEATED JOB].

First, interview me. Ask ONE question at a time and wait for my answer. Do not draft the final playbook until you have covered:
- what starts the task and how often it occurs
- the inputs needed and where they come from
- the exact steps, in the order I actually do them
- the decisions I make and the rules behind them
- how I recognise good and bad outputs
- the tone, format, and audience requirements
- past errors, edge cases, and exceptions
- what I check before calling the job finished

Ask follow-up questions whenever an answer is vague. Give me a chance to add anything you missed.

When I say the interview is complete, produce:
1. A concise job title and a specific "When to use this" description.
2. A complete SKILL.md-style playbook with Purpose, Trigger, Inputs, Steps, Decision Rules, Definition of Done, and Edge Cases.
3. A list of missing files or resources to create next.
4. Two questions: What did I get wrong? What did you forget to tell me?

If you can write files, create a folder named [JOB-NAME] and place SKILL.md inside it. If you cannot, print the full file in chat and tell me exactly where to save it. Never claim you saved a file unless you did.

Tip: if you intend to install this as an Anthropic-compatible Skill, add the required YAML frontmatter, including name and description, to SKILL.md.

Layer 2

The toolbox: stop rebuilding the same things

The toolbox is the reusable material your job needs. When a template, script, checklist or approved example works, save a reusable version. Then link it from the playbook and say exactly when to use it.

Without this layer, an AI may recreate a new email format, caption structure or spreadsheet-processing script every time. You end up paying for repeated work while the output changes slightly on each run.

What belongs in a toolbox?

  • Reusable scripts that perform a predictable step.
  • Templates with placeholders for details that change each time.
  • Approved examples that show the desired standard.
  • Reference files, including naming rules and terminology.
  • Brand voice instructions and repeatable subtask prompts.

Don't save half-approved drafts, one-time outputs, credentials, or anything you wouldn't give a new teammate as a trusted reference.

Prompt 2: build the toolbox

Copy-paste prompt · 02 / Reusable resources
Review the task we just completed and the playbook for [JOB-NAME].

Find anything we had to create that we are likely to need again: a script, template, checklist, approved wording, data reference, or repeatable prompt.

For each reusable item:
1. Give it a descriptive filename and put it in [JOB-NAME]/files/.
2. Replace case-specific details with clear [PLACEHOLDERS], while keeping one approved filled-in example when helpful.
3. Update SKILL.md to link to the file by name and specify WHEN to use it.
4. Update files/INDEX.md with its filename, purpose, and date reviewed.
5. Do not save one-off work, unapproved drafts, passwords, private keys, or secrets.

Run the same task a second time using the new toolbox. Tell me what you reused and what you unexpectedly had to rebuild. Recommend one more reusable item if something was rebuilt.

If you cannot write files, output the complete contents of every proposed file, its location, and the updated index so I can save the files myself. Do not claim anything was saved unless it was.

Example toolboxes for four jobs

Content repurposing

hook-bank.md, caption-template.md, brand-voice.md, approved reference reels and a note explaining why certain hooks performed well.

Weekly client updates

numbers-pull.py, update-template.md, client-names.md, tone-rules.md, and two approved past updates.

Invoice reminders

Approved email templates for early and late reminders, an escalation policy, contact records stored securely, and a tone guide.

Hiring screens

role-brief.md, scorecard.md, approved sample assessments, and a consistent response template. Human review remains necessary for consequential decisions.

Layer 3

The proof: tell the AI what “done” actually means

Most people say “check your work” and hope the model catches mistakes. That is not enough. An effective proof layer lists things that can be checked independently of the AI's confidence.

A good check produces evidence. A number matches a source file. A URL opens. A word count is within the limit. A piece of code passes a test. A claim matches an approved reference. If a check cannot fail, it's probably too vague.

Prompt 3: add the proof layer

Copy-paste prompt · 03 / Acceptance tests
Add a "Definition of Done" and "Proof Checks" section to the playbook for [JOB-NAME].

Write 5–10 acceptance checks specific to this job. Each one must have an objective way to pass or fail, with evidence outside your own opinion.

Examples of acceptable evidence:
- a number cross-checked against a source document
- a link that actually loads
- a screenshot of the rendered output
- code tests that run and pass
- a claim matched to a specific source
- a count, filename, or spelling checked against a reference

Avoid vague checks such as "looks great" or "is professional".

For every future run of this playbook:
1. Complete the task.
2. Perform all available checks.
3. Correct what fails, then test again.
4. Return a PASS, FAIL, or NOT VERIFIED result for each check with its evidence.
5. State clearly what you could not verify. Never pretend a test ran or a link was opened.
6. If several related checks fail, stop and identify the underlying process problem before making cosmetic fixes.

Update SKILL.md with these rules. If file editing is unavailable, show the entire revised section and explain where I should place it.

What a real proof check looks like

Content: the hook is within the requested word limit, the script fits the target duration at the intended pace, claims match their sources, and the CTA uses the approved keyword.

Client report: every figure matches its original data, the client's name matches the reference, and all outstanding actions are addressed.

Invoice reminder: amount, due date and recipient are correct, the payment destination has been verified, and the tone matches the reminder stage.

Hiring review: each assessment cites actual evidence from the application, and the reviewer flags missing or uncertain information instead of inventing a score.

The loop: fix the playbook, not the chat

When an output goes wrong, the tempting response is to type “No, that's not what I meant” and move on. The next time you run the task, the same problem returns because the correction never reached the playbook.

Instead, identify which layer failed. A missing step is a process problem. A reused file that is outdated or a template rebuilt from scratch is a toolbox problem. A mistake that should have been caught is a proof problem.

Prompt 4: diagnose and repair mistakes

Copy-paste prompt · 04 / Diagnose + improve
The last output for [JOB-NAME] was wrong because: [DESCRIBE THE SPECIFIC ERROR].

Do not simply fix the current chat response. Diagnose which layer failed:
- PROCESS: a step, decision rule, or exception was missing or wrong.
- TOOLBOX: a needed reusable file was missing, outdated, incorrectly selected, or rebuilt unnecessarily.
- PROOF: an acceptance check was missing or failed to detect the error.

Explain the root cause briefly and identify the smallest durable change that prevents a repeat.

Then:
1. Update the relevant section or file, not the whole playbook.
2. If the same mistake has occurred twice, add an explicit preventative rule.
3. Add a dated entry to [JOB-NAME]/notes.md describing the error and fix.
4. Rerun the same task and perform the proof checks.
5. Show the before-and-after result and tell me whether the change worked.

If you cannot directly edit the files, print the exact replacement text and file path. Do not claim the change is permanent until the master file has actually been updated.

Review the correction log regularly. If several problems keep returning in the same layer, that area deserves more attention. It may need a clearer rule, an improved template, or a real scripted test.

The folder, once it is built

One folder per job makes it easier to find the right instructions. Give each playbook a description that matches how you would naturally ask for that job to be done.

weekly-client-update/ ├── SKILL.md # purpose, inputs, steps, decisions, │ # proof checks and edge cases ├── files/ │ ├── INDEX.md # reusable items and their purpose │ ├── numbers-pull.py # validated data extraction │ ├── update-template.md │ └── tone-rules.md ├── examples/ │ ├── approved-update-01.md │ └── approved-update-02.md └── notes.md # dated corrections and outcomes

For an actual Claude-compatible Skill, add frontmatter to SKILL.md. Only include scripts the AI can safely execute in its environment, and confirm permissions before it accesses sensitive systems.

A small example of SKILL.md

--- name: weekly-client-update description: Prepare the weekly client performance update when asked to report results or progress. --- # Weekly client update ## Inputs - Approved reporting data - Previous week's commitments - Client naming and style reference ## Steps 1. Read the latest approved reporting file. 2. Compare results to the target and prior period. 3. Draft using files/update-template.md. 4. Check results against the source data. ## Definition of done - Every number matches the source. - Client name matches the approved reference. - Every action promised last week is addressed. - Flag missing data; never invent a value.

A full worked example: your weekly client update

Process. In the interview, you explain that you open the ads dashboard, compare last week's results with the plan, identify the biggest change, and write a short update in a direct voice. That ordering becomes part of the process.

Toolbox. After one approved run, save the data-pull script, report template, correct client spellings, and one strong example. Link each item in the playbook so the AI knows where to find it.

Proof. Require each figure to match the source, keep the report within the agreed length, use the client's approved name, and account for last week's promised action.

Loop. Imagine the next report includes a figure that is absent from the dashboard. Record that as a proof failure, add an explicit source-verification check, and rerun the report. The key is to confirm the check catches the error on a second run, not merely to tell the AI to be more careful.

Over time, you should be spending more attention reviewing finished work and less time repeating the same instructions. Keep a human sign-off for important external communications and any high-stakes decisions.

Five mistakes to avoid

  1. Writing a generic process from memory. Let the interview reveal your actual decisions and exceptions.
  2. One huge folder for every task. Separate jobs clearly so the model can find the right material.
  3. Vague playbook descriptions. Explain exactly when the AI should use each playbook.
  4. Skipping the proof layer. “Looks fine” is not evidence that a task was done correctly.
  5. Correcting only in chat. Change the real master file and check that the fix survives a new run.

Your first thirty minutes

Start with one regular task. Treat thirty minutes as a suggested first session, not a guarantee that complex jobs can be documented and tested that quickly.

Don't stop after writing the playbook. The second run tells you what was really reusable, what is still unclear, and which proof checks need work.
